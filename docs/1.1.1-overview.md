# jflux 1.1.1 implementation notes

JFlux 1.1.1 completes the encrypted API session-capacity redesign.

## Session capacity

Capacity is now tracked per root API key rather than by a global server
`max_sessions` value. A key starts at one session. Authenticated allocation
tokens increase that key's limit, while `session/reset` invalidates all of the
key's live sessions and reservations and returns the limit to one. When the
durable resume store is configured, the allocation ledger is persisted beside
its metadata file as well.

Live sessions and outstanding close-generated resume tokens both consume a
slot. A valid resume replaces its reservation, so resuming remains possible at
the limit. New initialization at capacity receives a specific 429 response
that recommends resume or reset.

## Allocation security

`session/allocate` is backed by a one-time challenge and a signed allocation
assertion. JFlux does not receive usernames, passwords, MFA values, or OAuth
tokens. The external web-authentication backend performs manual user
authentication and signs the challenge with the private
`session_allocation_secret` associated with the API key. JFlux verifies that
signature, consumes the challenge once, and increases capacity by exactly one.
The shared secret is persisted with the encrypted API-key record and never
crosses the network.

## Resume security

Resume tokens are created only by an authenticated `session/close` request when
the client explicitly asks for one. Raw tokens are never persisted by the
server; only hashed metadata is stored. Replay or API-key mismatch resets all
sessions and token state for that API key. Client-side resume stores can be
file-backed and are cleared after reset or ordinary close.

An authenticated `session/heartbeat` request refreshes the inactivity deadline
for an existing session and advances the normal encrypted ratchet. It never
allocates a session and never creates a resume token. Clients should use it
periodically while the application is running, then request a resume token only
on the explicit shutdown close request.
