# jflux 1.1.0 implementation notes

## Scope

jflux 1.1.0 is being developed package by package. The goals are lower allocation
overhead, predictable memory use, simpler public APIs, and smaller runtime artifacts
where the package split allows it.

The current artifact split is retained for compatibility:

- `jflux-${version}-core.jar` for general utilities
- `jflux-${version}-db.jar` for database support
- `jflux-${version}-http.jar` for HTTP/API support
- `jflux-meridiandb-${version}.jar` and the full shaded jar for existing consumers

Downstream projects currently reference 1.0.6 artifacts. Those references should be
migrated only after each package change has passed the jflux tests and a consumer
compatibility build.

Cloud remains in the compatibility inventory but is not a required early package
target. It brings large provider SDK dependencies and should be handled separately
from the small core utility packages.

## Package order

The initial order is based on consumer reach and ability to validate behavior without
changing a protocol or storage format:

1. `encoding` (completed)
2. `crypto` (adapter and PQC foundation completed)
3. `files` (completed), `exceptions` (completed), `sys`, and `shell`
4. `threading` (completed) and `sockets` (completed)
5. `todash`, `json`, `output`, and `csv`
6. `db`
7. `http`
8. optional/provider packages such as `cloud`, email, SSL, and integrations

Each package change must retain existing public entry points where practical, add
focused tests for edge cases, and update the package documentation in this directory.

## Cross-package exception migration

The completed `encoding`, `crypto`, and `files` work now uses
`com.fortrow.jflux.exceptions.ExceptionHandling` at legacy error boundaries. This
centralizes automatic logging and optional reporting while preserving existing
nullable results, sentinel byte arrays, and runtime exception contracts where
downstream STRATO applications depend on them. New package work must use the
jflux exception types directly or pass compatibility failures through this bridge.

The `com.fortrow.jflux.mcp` package now provides a JSON-RPC MCP server/client pair
and the MCP exception reporter. It supports stdio and JDK HTTP transport adapters
without adding an MCP SDK dependency to the core artifact.

The `sys` and `shell` milestone now provides structured, bounded command
execution; cross-platform package auditing and installation; Java metadata
helpers; and language-neutral Git/wget source installer composition. Legacy shell
entry points delegate to the shared runner.

The `threading` milestone now uses virtual-thread-backed lifecycle helpers,
bounded executor queues, explicit worker termination, and consistent exception
reporting for background failures.

The `sockets` milestone now uses Java 21+ virtual threads for accept/session
work, UTF-8 line framing, idempotent close callbacks, lifecycle observation, and
blocking session reads without polling delays.

The `todash` milestone modernizes the historical `__` facade with reusable
patterns, null-safe/value-aware helpers, lower-allocation console and string
operations, and a focused Lodash-style collection API without adding a runtime
dependency.

The `json` milestone now uses JSON-Simple for the default parse and compact
serialization path, caches Gson only for explicit typed conversion and pretty
formatting, restores object/array compatibility helpers, and keeps the legacy
`com.fortrow.jflux.json.JSON` namespace as a delegating facade. See
[`json.md`](json.md) for the strict and legacy API behaviors.

The `http` milestone is now applying the redefined exception model across REST
and encrypted API boundaries. It adds reportable `APIException` failures,
bounded request-body reads, strict JSON/required-parameter validation, safer
timestamp/header handling, and explicit HTTP 413 responses for oversized bodies.
See [`http.md`](http.md) for the current request and client resource behavior.
